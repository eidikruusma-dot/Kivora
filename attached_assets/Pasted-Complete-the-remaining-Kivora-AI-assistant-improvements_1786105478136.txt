The system correctly sets:

importAllowed = false

but the extraction itself must now be made reliable.

REQUIRED ARCHITECTURE:

1. Process the PDF PAGE BY PAGE.

Do not rely on one giant vision request for the entire PDF.

For each page:
- send that page or page-specific PDF input to OpenAI vision/file processing
- extract only the transaction rows visible on that page
- preserve:
  - page number
  - row order
  - date
  - exact description
  - debit amount
  - credit amount
  - currency

Return structured JSON only.

2. Keep debit and credit as separate source fields.

Canonical transaction structure should contain something equivalent to:

{
  page: number,
  rowIndex: number,
  date: "YYYY-MM-DD",
  description: string,
  debit: number | null,
  credit: number | null,
  amount: number,
  direction: "income" | "expense",
  currency: "EUR",
  needsReview: boolean
}

3. Direction must be deterministic.

If credit > 0:
direction = income

If debit > 0:
direction = expense

Never infer direction from:
- description
- person's name
- merchant
- words like loan, insurance, transfer, savings, payment

If both debit and credit exist or neither can be determined:
needsReview = true

4. Date parsing.

SEB Estonia uses European dates.

DD.MM.YYYY must always become:
YYYY-MM-DD

Examples:
07.08.2026 → 2026-08-07
06.08.2026 → 2026-08-06
01.08.2026 → 2026-08-01

Never interpret DD.MM as MM.DD.

5. Process ALL pages.

The backend must know:
- total PDF page count
- pages successfully processed
- pages failed

extractionComplete cannot be true unless every page is processed successfully.

6. Merge all page results in application code.

Do not ask the LLM to calculate final totals.

Application code must calculate:

incomeCount
expenseCount
totalIncome
totalExpenses

from the canonical validated transaction array.

7. Reconciliation.

Read the statement's own summary:
- opening balance
- closing balance
- total income
- total expenses
- period

Compare it against the canonical transaction array.

8. Automatic recovery pass.

If reconciliation fails:

Run a second targeted extraction ONLY for the pages where:
- rows appear missing
- totals do not reconcile
- OCR confidence/readability was poor

The second pass must receive the ORIGINAL visual page, not the first-pass extracted text.

Provide the already-found rows to avoid duplicates.

Merge only genuinely missing/corrected rows.

C. EDIT AND DELETE AI CHAT MESSAGES
==================================================

Add message editing and deletion.

USER MESSAGES:

1. Every user-created chat message should have actions:
- Edit
- Delete

Use either a small menu (⋯) or the existing Kivora interaction pattern.

Do not clutter every bubble with large permanent buttons.

2. EDIT:

When the user chooses Edit:
- open the message text in an editable textarea
- preserve the original attachments
- allow text changes
- Save
- Cancel

After Save:
- update the message in Firestore
- update updatedAt
- visually update the conversation immediately

3. Conversation consistency after edit:

Editing an old user message changes the context of later AI messages.

Do NOT pretend later AI responses are still guaranteed to match the edited message.

Use one of these safe behaviours:

Preferred:
When editing a user message that has later assistant messages:
- warn:
  "Selle sõnumi muutmine muudab vestluse konteksti. Kas soovid sellest kohast vestluse uuesti jätkata?"
- after confirmation:
  - update the message
  - remove later AI/user messages from that branch OR create a new branch from the edited message
  - regenerate only when the user explicitly asks

Do not silently keep contradictory future responses.

4. Attachments:

Editing message text must not:
- delete attachment metadata
- reveal hiddenContext
- convert hidden file context into visible text

5. DELETE:

User can delete their own message.

If deleting the latest isolated user message:
- delete normally

If deleting a message that has later conversation dependent on it:
show a warning.

Recommended:
"Kui kustutad selle sõnumi, eemaldatakse ka sellele järgnevad vestlussõnumid. Kas jätkata?"

Only delete after explicit confirmation.

6. Assistant messages:

Allow the user to delete assistant messages as well.

Editing assistant-generated text is NOT required unless there is already a product reason for it.

For assistant messages:
- Delete is sufficient.

7. Firestore:

Use the existing conversation/message schema.

Do not create a parallel chat history system.

Add store functions equivalent to:
- updateChatMessage(...)
- deleteChatMessage(...)
- deleteMessagesAfter(...)

Reuse existing conversation store architecture.

8. Internal fields:

Never expose or allow the user to manually edit:
- hiddenContext
- actions
- attachment extraction data
- internal tool results
- internal action payloads

Only visible user content is editable.

9. RAW INTERNAL JSON MUST NEVER BE SHOWN.

The user has previously seen responses like:

{
  "reply": "...",
  "actions": [...]
}

This must never appear in the visible chat.

The UI should render only:
reply

Actions remain internal.

Add a final defensive parser:
if the AI response contains the expected JSON wrapper,
extract reply for display and keep actions internal.

If malformed:
show a safe localized error instead of dumping raw JSON.
