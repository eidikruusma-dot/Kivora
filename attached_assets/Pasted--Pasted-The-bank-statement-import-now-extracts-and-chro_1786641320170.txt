Final report

Where 937.90 was being extracted from

A per-day summary row on an early page of the statement, labeled simply "Laekumised" (the Estonian word for "payments received / income"), with value 937.90. In SEB statements this label appears once per calendar day as a daily credit subtotal — not as a statement-wide period total.

Why it was incorrectly treated as statement-wide income

The old INCOME_PATTERNS included /\blaekumised\b/i — a bare word match with no scope qualifier. The extraction loop processes rows in page/row order and takes the first match; subsequent matches are discarded (with a conflict warning only if the values differ). The daily "Laekumised 937,90" row on page 1 was encountered before any statement-wide label, so 937.90 was locked in and the true total (if any exists on the statement) was silently ignored.

New rule for statement-wide printed totals

A row may only populate printedIncomeTotal or printedExpenseTotal when its label unambiguously scopes to the entire statement period. Two independent defences were added:

Tightened patterns — every INCOME_PATTERNS and EXPENSE_PATTERNS entry now requires an explicit scope qualifier: the Estonian "kokku" (= total/altogether) or unambiguous English multi-word phrases ("total income", "income total", "total credits", etc.). Bare words laekumised, sissetulekud, väljaminekud were removed.

DAILY_SCOPE_EXCLUSION_PATTERNS — belt-and-suspenders. Even if a future pattern could match, any row also containing päeva, kreeditkäive, deebetkäive, daily, subtotal, vahesumma, pending, or reserveeritud is skipped with a warning. Applied only to printed income/expense totals; opening/closing balance patterns are inherently statement-level and need no extra filter.

Missing printed totals are treated as "control unavailable" — they never produce a failure. The running-balance chain (opening → each posted transaction → closing) remains the primary and strongest validation.

What was implemented
parseBankCsv.ts — deterministic CSV/Excel parser

Concern	Approach
File formats	CSV (any delimiter auto-detected via frequency count on first non-empty row), Excel .xlsx/.xls via xlsx CJS package (multi-sheet: first sheet with more than 5 rows is used)
BOM / encoding	BOM stripped before parsing; UTF-8 assumed
Quoted fields	Full RFC 4180 quoted-field support including embedded newlines
Column detection	Scores each header cell against scored regex patterns for date, description, debit, credit, amount (signed), balance, currency, status; highest scorer wins per role; ambiguous layouts fall back to positional heuristics
Date parsing	DD.MM.YYYY, DD/MM/YYYY, YYYY-MM-DD, MM/DD/YYYY, DD-MM-YYYY all normalised to YYYY-MM-DD
Amount parsing	European (1.234,56) and international (1,234.56) formats; negative credit treated as debit and vice-versa
Control rows	SKIP_PATTERNS filters section headers, running totals, and label rows that match but contain no amounts
Opening/closing balance	Detected from control rows (saldo alguses, opening balance, closing balance, lõppsaldo, etc.)
Pending section	Section header (row matching pending keyword with no valid date and no amounts) sets inPendingSection = true; subsequent rows marked pending: true; status column values matching reserved/pending/ootel/blokeeritud also mark individual rows pending
