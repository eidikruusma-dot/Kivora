The model must:

- preserve every genuine transaction exactly once
- keep debit and credit separate
- never infer direction from merchant/payee text

- merge multi-line descriptions belonging to one transaction
- return low confidence rather than guessing when a row is unclear

- return null when metadata is absent
- never calculate missing printed totals itself

6. REMOVE CONTROL TOTALS AS A HARD REQUIREMENT
==================================================

This is critical.

A bank statement is NOT invalid merely because the model cannot find:

printedIncomeTotal
printedExpenseTotal
openingBalance
closingBalance

Different banks and statement formats expose different metadata.

Therefore:

Missing printed totals MUST NOT automatically set extractionComplete=false.

Missing opening/closing balances MUST NOT automatically set extractionComplete=false.

Instead introduce validation status:

"verified"
"review_required"
"unverified"

Meaning:

VERIFIED:
- extraction structurally valid
- no ambiguous transactions
- AND at least one available independent control check matches

UNVERIFIED:
- transactions structurally valid
- no ambiguous transactions
- but no independent control totals/balance pair are available

REVIEW_REQUIRED:
- ambiguous transaction rows
- duplicate uncertainty
- malformed dates
- both debit+credit
- neither debit+credit
- explicit control totals are present AND materially disagree with calculated totals
- clear balance contradiction

IMPORTANT:
UNVERIFIED is NOT the same as INVALID.

A user must still be allowed to open the review card and manually confirm an UNVERIFIED statement after reviewing the transactions.

Do not tell the user that their statement is wrong merely because summary totals were not printed/read.

==================================================
7. RECONCILIATION
==================================================

Calculate in application code only:

calculatedIncomeTotal
calculatedExpenseTotal
incomeCount
expenseCount

If printedIncomeTotal exists:
compare against calculatedIncomeTotal.

If printedExpenseTotal exists:
compare against calculatedExpenseTotal.

If both openingBalance and closingBalance exist:
compare:

openingBalance + income - expenses ≈ closingBalance

If a control value does NOT exist:
skip that check.

Do not invent a failure for missing controls.

==================================================
8. RUNNING BALANCE VALIDATION
==================================================

Do NOT use running balance as a mandatory validation source.

Only use it if:
- a reliable balance value exists for consecutive rows
- transaction ordering can be determined safely
- the mathematical relationship is clear

If not reliable, skip it.

A running-balance heuristic must never mass-flag transactions simply because the PDF layout is unfamiliar.
