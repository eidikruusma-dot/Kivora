TASK 1 — TRANSACTION ORDER

After extraction and normalization, sort bank transactions deterministically
from oldest to newest before reconciliation.

For transactions on the same date, preserve the statement's actual running-balance
sequence. Do not arbitrarily reorder same-day transactions by description or amount.

If row/page metadata is needed to preserve statement order, use it.

TASK 2 — RUNNING BALANCE RECONCILIATION

Where the statement provides a running balance, validate the transaction chain.

For each consecutive posted transaction:

previousBalance
+ credit
- debit
≈ currentBalance

Use a 0.01 EUR tolerance.

A mismatch must flag the relevant transaction for review and block automatic import.

Do NOT use the running balance to decide whether a transaction is income or expense.
Direction still comes only from debit/credit columns.

TASK 3 — OPENING/CLOSING BALANCES

Use opening and closing balances as controls, but respect chronological order.

Validate:

opening balance
→ chronological posted transactions
→ closing balance

Do not simply sum transactions in the PDF's top-to-bottom display order.

TASK 4 — DAILY/SUMMARY ROWS

Rows representing things such as:

- debit turnover / deebetkäive
- credit turnover / kreeditkäive
- daily balance / päeva jääk
- opening balance
- closing balance
- subtotals / totals

are CONTROL ROWS, not transactions.

Never import them as income or expense.

Use them only for validation when their meaning is unambiguous.

TASK 5 — RESERVED/PENDING CARD PAYMENTS

Do not mix reserved/pending card payments with posted/booked transactions.

If the statement contains a separate reservations/pending section:

- classify them separately
- do not include them in posted income/expense totals
- do not use them in the posted running-balance chain unless the statement
  explicitly defines that balance as including reservations
- do not write them to Firestore as normal posted transactions

If the current BankTransaction model cannot represent pending/reserved status,
report that first and propose the smallest safe model extension.
Do not guess.

TASK 6 — PRINTED TOTALS

Printed statement totals are secondary controls.

Do not block an otherwise internally consistent transaction chain merely because
a label was misidentified as "printed income total".

First determine what the printed field actually represents.

The strongest controls should be:

1. transaction running-balance chain, when present
2. opening → posted transactions → closing balance
3. clearly identified printed debit/credit turnover totals
